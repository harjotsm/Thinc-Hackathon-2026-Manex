Schritt 4 ist der einzige Punkt, an dem der Engineer aktiv entscheiden muss — und an dem der Manager bei hoher Severity mit co-signieren muss. Schritt 5 läuft in vier Sub-Spuren parallel: System persistiert & überwacht, Operator sieht Bestätigung, Engineer trackt seine Initiativen, Manager sieht Portfolio.

Abschnitt 6

Lifecycle einer Initiative

stateDiagram-v2
  [*] --> Signal : Trigger (System 1A oder Operator 1B)
  Signal --> Classified : Archetyp zugeordnet
  Classified --> Investigating : Agent-Loop laeuft
  Investigating --> Investigating : next tool call
  Investigating --> Stalled : low confidence
  Stalled --> Investigating : Engineer gibt Hint
  Investigating --> Evidenced : confidence ≥ threshold
  Evidenced --> Drafted : Report D1..D8 + Initiative-Kandidaten
  Drafted --> UnderReview : Engineer Review
  UnderReview --> Drafted : amend
  UnderReview --> EscalatedToManager : critical severity
  EscalatedToManager --> Approved : Manager co-signs
  UnderReview --> Approved : non-critical
  Approved --> Persisted : INSERT product_action
  Persisted --> InFlight : status=in_progress
  InFlight --> Closed : status=done + Closure-Metrik erfuellt
  InFlight --> Reopened : Closure fehlgeschlagen
  Reopened --> Investigating
  Closed --> [*]
Closure ist verifizierbar, nicht stempelbar: z.B. „keine SOLDER_COLD-Defekte bei PM-00008 in den nächsten 4 Wochen". Der Closure-Monitor (O5) prüft das gegen den Live-Datenstream — und re-triggert automatisch, wenn das Pattern wiederkommt. Das ist der Pillar-3-Hebel.
